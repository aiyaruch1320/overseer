# แผนลงโค้ด

ภาพรวม: [README.md](README.md) · แผนรวม: [../../RAW_PLAN.md](../../RAW_PLAN.md) หัวข้อ 4.7 · การจัดเอกสาร: [organization.md](organization.md) · รหัส: [id-glossary.md](id-glossary.md)

เขียน 2026-11-02 หลังชั้นเอกสารครบ ไฟล์นี้คือคู่มือของ session ที่ลงมือเขียนโค้ด อ่านไฟล์นี้ไฟล์เดียวแล้วเริ่มงานได้ ทุกหัวข้อชี้ไปยังเอกสารที่เป็นแหล่งความจริง

## 0. วิธีใช้ไฟล์นี้

1. อ่านหัวข้อ 1 (ที่ตัดสินแล้ว) และหัวข้อ 2 (สถาปัตยกรรม) ก่อนทำอะไร
2. ทำตามขั้นในหัวข้อ 11 ตามลำดับ ขั้นหนึ่งเสร็จเมื่อผ่านด่านในหัวข้อ 10
3. แบ่งงานให้ subagent ตามหัวข้อ 12 ใช้แบบฟอร์มคำสั่งในหัวข้อ 12.4 และจบทุกรอบด้วยรอบตรวจของผู้เล่นจำลอง (หัวข้อ 12.6)
4. เมื่อโค้ดกับเอกสารขัดกัน เอกสารชนะ ถ้าเอกสารผิดจริง แก้เอกสารก่อน แล้วสร้างข้อมูลใหม่ ไม่แก้ข้อมูลที่สร้างด้วยมือ
5. บันทึกความคืบหน้าใน `review/progress.md` ทุกครั้งที่จบงานย่อย (หัวข้อ 15) และสถานะในตารางหัวข้อ 11
6. ทำงานต่อเนื่องเป็น session ยาวโดยไม่หยุดถามผู้ใช้ (หัวข้อ 1 แถว "การตัดสินใจระหว่างทาง") แล้วรายงานครั้งเดียวตอนจบ (หัวข้อ 16)

## 2. สถาปัตยกรรม

```
docs/ (แหล่งความจริง)
  │  scripts/codegen/*  อ่านตาราง ตรวจ แล้วเขียน
  ▼
data/gen/*.json  (ข้อมูลที่สร้าง เข้า git)        data/library/*.jsonl (คลังชั้น 1 ที่มีอยู่แล้ว)
  │                                                │
  ▼                                                ▼
src/core/  แกนจำลอง ไม่มีจอ ไม่มี DOM ไม่มี Phaser  ── src/core/text/ (แม่แบบชั้น 0 คลังชั้น 1 ชื่อ)
  │  สถานะ + คำสั่ง + บันทึกเหตุการณ์
  ▼
src/app/   ชั้นเชื่อม: ถือเกม ส่งคำสั่ง แปลงบันทึกเป็นสิ่งที่จอต้องแสดง (การเรียก ฉาก การ์ด)
  │
  ├─ src/ui/      หน้าจอ DOM (Preact) แผง การ์ด หน้าหยุด หน้าเกิด หน้าจบ
  ├─ src/map/     แผนที่ห้าระดับซูม (Phaser) ผ่านตัวให้ภาพที่เปลี่ยนได้
  ├─ src/scene/   ตัวเล่นฉาก (cutscene) อ่านสคริปต์ฉากจากข้อมูล
  └─ src/art/     ตัววาดตัวละคร ศัตรู มังกร ไอเทม (เวกเตอร์ด้วยโค้ด)
server/  API ของ LLM เซฟ และบันทึกการเล่น (มีอยู่แล้ว แก้ตาม LLM สามจุด)
```

**หลัก**

1. **แกนไม่รู้จักจอ** `src/core/` ไม่ import อะไรจาก `src/app/` `src/ui/` `src/map/` `src/scene/` `src/art/` ตรวจด้วยกฎ import ในตัวทดสอบ
2. **กำหนดได้** ทุกการสุ่มผ่านสายเมล็ดที่แยกตามระบบ (หัวข้อ 6.2) เมล็ดเดิมได้ชีวิตเดิมทุกครั้ง ค่าที่ LLM ตอบบันทึกลงเซฟ
3. **ข้อมูลไม่เขียนมือ** ทุกตารางของเกมมาจาก `data/gen/` ซึ่งสร้างจากเอกสาร ค่าที่ไม่มีในเอกสารแต่โค้ดต้องใช้ (เช่น ความเร็วของแอนิเมชัน) อยู่ใน `src/**/tuning.ts` ที่เดียวต่อระบบ
4. **สองนาฬิกา** ปีโลก ศ.ม. (ก้าวทีละทศวรรษสำหรับโลก ทีละปีเมื่อมีตัวละครอยู่) และปีชีวิต (สี่ช่วงต่อปีสำหรับตัวละคร) ตาม [../lore/world/world-time.md](../lore/world/world-time.md)
5. **ทุกระบบมีเป้าที่ทดสอบได้** เป้าที่ตัวจำลองระดับเอกสารวัดไว้ (`scripts/sim/`) กลายเป็นเทสต์ของแกนจริง
6. **ภาพเปลี่ยนได้** ทุกสิ่งที่วาดผ่านตัวให้ภาพ (หัวข้อ 8.4 และ 9) จอไม่รู้ว่าภาพมาจากโค้ดหรือไฟล์ภาพ

ไวยากรณ์ทั้งหมดอยู่ใน `scripts/codegen/lib/effects.ts` ชนิดของผลและเงื่อนไขอยู่ใน `src/core/types.ts` คำที่เหลือจากการแปลที่ไม่ใช่รหัส เก็บเป็นป้าย (`label`) หรือเงื่อนไขข้อความ (`text`) เงื่อนไขข้อความประเมินไม่ได้ จึงต้องแก้เป็นรูปแบบในตารางนี้ถ้ามันกั้นทางจริง

ขั้นทำ: (1) เขียนตัวแปลตามตารางนี้ (2) รันกับทุกไฟล์ เก็บวลีที่ดูเหมือนผลแต่แปลไม่ได้ (มีตัวเลข ร้อยละ ×) (3) เพิ่มรูปแบบที่พบบ่อยลงตารางนี้และใน [id-glossary.md](id-glossary.md) (4) วลีที่เหลือ แก้ในเอกสารให้ตรงรูปแบบ ทีละไฟล์ ใช้ subagent ร่างและตัวตรวจยืนยัน รายงานส่วนที่แปลไม่ได้ต้องว่างก่อนขั้นที่ใช้ข้อมูลนั้น

### 5.3 รุ่นของข้อมูล

## 8. UI

### 8.0 หน้าทดสอบช่วงทำระบบ

ระหว่าง M1 ถึง M4 ยังไม่ลงแรงกับ UI แต่ทุกระบบต้องเล่นและตรวจได้ จึงมีหน้าทดสอบสองแบบ ใช้ได้ทั้งคนและ subagent

| แบบ | ทำอะไร | ใช้โดย |
| --- | --- | --- |
| เล่นทางบรรทัดคำสั่ง | `npm run play -- --seed=N [--persona=ชื่อ] [--cmd="..."]` เดินชีวิตทีละจังหวะ แสดงสิ่งที่ผู้เล่นจะเห็นเป็นข้อความ (บันทึกเรื่องราว การเรียก การ์ด หน้าหยุด ตัวเลือกของพระเจ้า) รับคำสั่งพระเจ้าเป็นข้อความ เก็บสถานะไว้ในไฟล์ จึงเล่นต่อกันหลายคำสั่งได้ | subagent ผู้เล่นจำลอง (หัวข้อ 12.6) |

1. **UI เริ่มหลังระบบเสร็จ** (ขั้น M5 ถึง M7) ก่อนหน้านั้นใช้หน้าทดสอบ (หัวข้อ 8.0) ทุกหน้าจอใช้งานได้เต็มด้วยภาพที่วาดด้วยโค้ดหรือภาพแทนก่อนลงแรงกับภาพ

3. สี ขนาด ฟอนต์ มาจาก token ชุดเดียว (`src/ui/tokens.ts`) ตาม [../appearance/20-god-ui.md](../appearance/20-god-ui.md) หัวข้อ 1 และค่า UI ของทวีปใน [../appearance/01-continents.md](../appearance/01-continents.md)

5. หน้าจอทุกหน้าเปิดได้จากหน้า storybook ภายใน (`/dev.html`) พร้อมสถานะตัวอย่าง เพื่อตรวจโดยไม่ต้องเล่นถึงจุดนั้น

## 9. ภาพตัวละคร

### 9.1 ท่อ

```
docs/appearance/02-races.md (ค่า UI ต่อเผ่า)  ─┐
docs/appearance/npcs/*.md (ค่า UI ต่อ NPC)     ├─ codegen → data/gen/looks-*.json → src/art/ (ตัววาดพิกเซล) → แผ่นสไปรต์ → texture ของ Phaser
docs/appearance/19-ally-successors.md          │                                                   └→ เฟรมบนแคนวาสเล็ก (ภาพเหมือนบนการ์ด DOM)

```

แนวภาพคือพิกเซลอาร์ต สัญญาของภาพ (ขนาดเฟรม โทนสี เส้นขอบ ท่า ซูม) อยู่ที่ [../appearance/21-pixel-art.md](../appearance/21-pixel-art.md) ตัววาดอ่าน **Look** วาดวัสดุแบนลงตาราง แล้วลงเงาสี่โทนและเส้นขอบเอง จากนั้นอบเป็นแผ่นสไปรต์ในเครื่องของผู้เล่น (ไม่มีไฟล์ภาพตัวละครใน repo) ตัวต้นแบบอยู่ที่ `src/lab/art/pixel.ts` (ห้องทดลอง `art-lab.html`)

`legacy/render/characters/` (เวกเตอร์) ไม่ใช้วาดแล้ว แต่เป็นที่มาของรายการ: ท่า 55 ท่า ธีมเผ่า 21 ชุด ชุด 26 แบบ ผม 14 ทรง หมวก 21 แบบ เครื่องมือ 30 ชนิด ปีก หาง สไลม์ ห้าช่วงวัย ตัววาดพิกเซลต้องมีชิ้นส่วนครบชุดนี้

### 12.2 กติกา

1. **ไฟล์มีเจ้าของคนเดียว** agent แก้ได้เฉพาะไฟล์ในคำสั่งของตน ถ้าต้องเปลี่ยน `types.ts` หรือไฟล์ของคนอื่น เขียนข้อเสนอในรายงาน ผู้นำเป็นคนแก้
2. **ใช้ worktree แยก** งานเขียนโค้ดใช้ `isolation: "worktree"` agent ได้สำเนาโค้ดและสาขาของตัวเองที่แตกจาก `code-phase` ล่าสุด งานแก้เอกสารไฟล์เดียวและงานอ่านอย่างเดียว (ผู้ตรวจ ผู้เล่นจำลอง ผู้ตรวจภาพ) ทำใน checkout ของผู้นำได้ (หัวข้อ 12.7)
3. **พร้อมกันไม่เกินห้า agent** และไม่ให้สอง agent แก้เอกสารไฟล์เดียวกัน
4. **ทุกงานจบด้วยด่าน** agent รัน typecheck test และ docs:verify (ถ้าแตะเอกสาร) ก่อนรายงาน
5. **commit ในสาขาของตัวเอง ไม่ push** agent ที่ทำงานใน worktree commit งานในสาขาของตัวเองทีละขั้นที่ผ่านด่าน (งานจึงไม่หายถ้าติดเพดานกลางทาง) ห้าม push ห้ามแตะสาขา `code-phase` และ `main` agent ที่ทำงานใน checkout ของผู้นำไม่ commit ผู้นำ commit ให้ ข้อความ commit ทุกตัวสั้น ไม่มีบรรทัด attribution ตามกติกาของผู้ใช้
6. **เอกสารผิด** agent ไม่แก้ตรรกะให้ผิดจากเอกสาร ให้รายงานพร้อมข้อเสนอ ผู้นำตัดสินและแก้เอกสารเอง บันทึกใน `review/decisions.md`
7. **ไม่แตะ** `src/` นอกงานของตน `legacy/` (อ่านได้) `data/library/` (ยกเว้นงานคลัง)


### 12.5 ผู้นำตรวจอะไรก่อนรวม

1. รายงานของ agent ครบหกส่วนตามแบบฟอร์ม 12.4
2. `git diff code-phase...<สาขาของ agent> --stat` มีเฉพาะไฟล์ที่ agent เป็นเจ้าของ
3. ด่านผ่านบนสาขาของ agent
4. สุ่มอ่านโค้ดหนึ่งไฟล์และเทสต์หนึ่งไฟล์เทียบเอกสาร
5. งานจอ: เปิดใน storybook หรือเล่นจริง ถ่ายภาพ

### 12.6 รอบตรวจของผู้เล่นจำลองและผู้ตรวจภาพ

ผู้ใช้ต้องการให้ทุกรอบมี subagent สวมรอยเป็นผู้เล่นหรือผู้ชม ลองเล่นหรือดูภาพ แล้วให้ feedback เพื่อพัฒนาต่อเนื่อง

**บุคลิกของผู้เล่นจำลอง** (เลือกตามรอบ ใส่ชื่อบุคลิกในคำสั่ง)

| บุคลิก | เล่นอย่างไร | สนใจอะไร |
| --- | --- | --- |
| ผู้มาใหม่ | ไม่อ่านคู่มือ กดตามที่เกมเรียก | เข้าใจไหมว่าเกิดอะไร ห้านาทีแรกได้ครบตาม [../systems/experience/01-one-life.md](../systems/experience/01-one-life.md) หัวข้อ 2 ไหม |
| ผู้อ่านเรื่อง | แทรกแซงน้อย ตามเรื่องตัวละคร | เรื่องต่อกันไหม ตัวละครทำตามนิสัยไหม ตอนจบเล่าถูกไหม |
| พระเจ้าเมตตา | ใช้พลังเต็มที่เพื่อช่วยตัวละคร | พลังพอไหม ช่วยแล้วเห็นผลไหม ราคาของการแทรกแซงมากเกินรู้สึกไหม |
| พระเจ้าผู้ลงโทษ | สาป ลงโทษ ทำลาย | ผลที่ตามมาเป็นเรื่องไหม ซากเป็นเรื่องไหม โลกตอบกลับไหม |
| นักหาช่อง | หาทางโกง ทำซ้ำ ใช้เพดาน | มีช่องที่ทำให้เกมเสียไหม ตัวเลขแตกไหม |
| ผู้เล่นซ้ำ | เล่นหลายชีวิตในโลกเดียว | ถ้อยคำซ้ำไหม สายตระกูลต่อเนื่องไหม ของสะสมดึงให้เล่นต่อไหม |

**ผู้ตรวจภาพ** สวมบทผู้ชมที่เห็นเกมครั้งแรก และผู้ตรวจที่ถือเอกสารรูปลักษณ์ ผู้นำถ่ายภาพหน้าจอ ภาพตัวละคร และลำดับภาพของฉาก (ด้วยเบราว์เซอร์ของ session) เก็บที่ `review/<รอบ>/` แล้วส่งรายการไฟล์ให้ผู้ตรวจภาพอ่าน (subagent อ่านไฟล์ภาพได้)

**สิ่งที่ส่งให้**

| ผู้ตรวจ | ได้อะไร |
| --- | --- |
| ผู้เล่นจำลองช่วงระบบ | คำสั่ง `npm run play` เมล็ด บุคลิก จำนวนชีวิต และเอกสารที่บอกว่าผู้เล่นควรรู้สึกอย่างไร ([../systems/experience/README.md](../systems/experience/README.md) [../systems/experience/02-hooks.md](../systems/experience/02-hooks.md)) |
| ผู้เล่นจำลองช่วง UI | ลำดับภาพของหนึ่งชีวิต (ภาพทุกครั้งที่เกมเรียก) และบันทึกเรื่องราว หรือเล่นผ่านเบราว์เซอร์ถ้า subagent มีเครื่องมือ |
| ผู้ตรวจภาพ | ภาพใน `review/<รอบ>/` และเอกสารรูปลักษณ์ของสิ่งที่อยู่ในภาพ |

**แบบ feedback** (ผู้ตรวจเขียนเป็นไฟล์ `review/<รอบ>/<บุคลิก>.md`)

```
บุคลิก · เมล็ดหรือภาพที่ใช้ · สิ่งที่ทำ
สิ่งที่เห็น: เล่าตามลำดับเหมือนผู้เล่นเล่าให้เพื่อนฟัง
สิ่งที่รู้สึก: สนุก งง เบื่อ รำคาญ ลุ้น ตรงไหน
ปัญหา: แต่ละข้อมี ระดับ (บล็อก หนัก กลาง เบา) · ที่เกิด · ทำซ้ำอย่างไร
ไม่ตรงเอกสาร: ข้อความหรือภาพที่ขัดกับเอกสาร พร้อมไฟล์และหัวข้อ
ข้อเสนอ: ไม่เกินห้าข้อ เรียงตามผลต่อประสบการณ์
```

**ผู้นำทำอะไรกับ feedback**

1. รวมทุกไฟล์ของรอบเป็นรายการเดียว `review/<รอบ>/triage.md` แยกเป็น บั๊ก · ไม่ตรงเอกสาร · ข้อเสนอการออกแบบ
2. บั๊กและสิ่งที่ไม่ตรงเอกสาร: แก้ในรอบถัดไป (ระดับบล็อกและหนักต้องแก้ก่อนขึ้นขั้นถัดไป)
3. ข้อเสนอการออกแบบที่เปลี่ยนเอกสาร: ผู้นำตัดสินเองตามหลักในหัวข้อ 16.1 แก้เอกสาร สร้างข้อมูลใหม่ รันด่าน แล้วบันทึกใน `review/decisions.md` (ไม่หยุดถามผู้ใช้)
4. รอบถัดไปใช้บุคลิกเดิมอย่างน้อยหนึ่งตัว เพื่อดูว่าปัญหาเดิมหายไหม
5. `review/` เข้า git เป็นประวัติของการพัฒนา

### 12.7 การ commit และการรวมงาน

```
main
 └─ code-phase            ผู้นำคนเดียวที่ commit merge และ push สาขานี้
     ├─ worktree ของ agent → สาขาของ agent (อยู่ในเครื่อง ไม่ push)
     └─ ...
```

**หนึ่งคลื่นงาน**

1. **ผู้นำเตรียม** commit สัญญากลาง (`types.ts`) และสิ่งที่คลื่นต้องใช้ลง `code-phase` แล้ว push
2. **ส่ง agent** พร้อมกันไม่เกินห้าตัว ด้วย `isolation: "worktree"` จดชื่อสาขาและที่อยู่ worktree ที่เครื่องมือตอบกลับลง `review/progress.md` ทันที (ส่วน "งานที่กำลังทำ") แล้ว commit + push ไฟล์นั้น
3. **agent ทำงาน** แก้เฉพาะไฟล์ของตน commit ในสาขาของตนทุกครั้งที่ผ่านด่านย่อย รายงานกลับพร้อมชื่อสาขาและ commit สุดท้าย
4. **ผู้นำรวมทีละสาขา** ตามลำดับที่ agent เสร็จ: ตรวจตามหัวข้อ 12.5 → `git merge --no-ff <สาขา>` เข้า `code-phase` → รันด่านทั้งหมด → อัปเดต `review/progress.md` (ย้ายงานจาก "กำลังทำ" ไป "บันทึก") ใน commit เดียวกับการรวม → push → ลบ worktree และสาขาของ agent
5. **merge ชนกัน** แก้เองถ้าเล็กและชัด ถ้าไม่ชัด ทิ้งสาขานั้น (`git merge --abort`) แล้วส่ง agent ใหม่จาก `code-phase` ล่าสุดพร้อมบอกสิ่งที่เปลี่ยน
6. **ด่านไม่ผ่านหลังรวม** ถ้าแก้ได้ภายในไม่กี่ไฟล์ แก้แล้ว commit แยก ถ้าไม่ได้ `git revert` การรวมนั้น push แล้วส่งงานแก้ให้ agent
7. **รอบตรวจ** หลังรวมครบทุกสาขาของคลื่น ผู้เล่นจำลองและผู้ตรวจภาพทำงานใน checkout ของผู้นำ เขียนไฟล์ใน `review/<รอบ>/` ผู้นำ commit + push ไฟล์เหล่านั้นและการแก้ตาม feedback ทีละเรื่อง

**งานที่ทำใน checkout ของผู้นำ** (แก้เอกสารไฟล์เดียว ผู้ตรวจ ผู้เล่นจำลอง ผู้ตรวจภาพ) agent ไม่ commit ผู้นำตรวจแล้ว commit + push เป็นงานละหนึ่ง commit ห้ามมีสอง agent แก้ไฟล์เดียวกันพร้อมกัน

**ข้อความ commit** สั้น บอกสิ่งที่เปลี่ยน ขึ้นต้นด้วยขั้นและคลื่น เช่น `M1 world: port the world clock and dragon falls` ไม่มีบรรทัด attribution

## 15. ทำงานต่อเนื่องและกลับมาทำต่อ

**ไฟล์ความคืบหน้า** `review/progress.md` คือความจำของงาน อ่านเป็นอย่างแรกทุกครั้งที่เริ่มหรือกลับมาทำต่อ

```
## สถานะ
ขั้นปัจจุบัน: M<n> คลื่น <ชื่อ>
งานที่กำลังทำ: <agent ที่ส่งไปและยังไม่รวม: งาน · สาขา · ที่อยู่ worktree · เวลาที่ส่ง>
งานถัดไป: <หนึ่งถึงสามข้อ>
ด่านล่าสุด: <ผลของ typecheck test docs:verify และเวลา>

## บันทึก (ใหม่อยู่บน)
<เวลา> · <สิ่งที่เสร็จ> · <commit>
```

**กติกา**

1. **commit บ่อย** จบงานย่อยแต่ละชิ้น (รวมสาขาของ agent หนึ่งตัว จบรอบตรวจ แก้เอกสารหนึ่งเรื่อง) แล้ว commit + push ทันที พร้อมอัปเดต `review/progress.md` ใน commit เดียวกัน งานที่เสร็จจึงไม่หายเมื่อ session หยุดกลางทาง
2. **progress บอกงานที่ค้างเสมอ** ทุกครั้งที่ส่ง agent จดชื่อสาขาและ worktree ก่อน ทุกครั้งที่รวมหรือทิ้ง ลบออกจากส่วน "งานที่กำลังทำ"
3. **ทำซ้ำได้** ทุกงานทำต่อจากกลางทางได้โดยไม่ทำงานที่ commit แล้วซ้ำ

**เมื่อกลับมาทำต่อ** (เริ่ม session ใหม่ หลังติดเพดาน หรือหลังลูปปลุก) ทำตามลำดับนี้ก่อนงานอื่น

1. อ่าน `review/progress.md`
2. `git status` ใน checkout ของผู้นำ: ไฟล์ที่ค้างและไม่อยู่ในงานใดที่จดไว้ ตรวจด่าน ถ้าผ่านและเป็นงานที่ตั้งใจ commit ถ้าไม่ชัด เก็บด้วย `git stash` แล้วจดไว้ใน progress
3. `git worktree list` และ `git branch`: ทุกสาขาของ agent ที่จดไว้ใน "งานที่กำลังทำ"
   - มี commit และด่านผ่าน → รวมตามหัวข้อ 12.7 ข้อ 4 แม้ไม่มีรายงานของ agent (ใช้ commit log แทนรายงาน)
   - มี commit แต่ด่านไม่ผ่าน หรือไม่มี commit → ส่ง agent ใหม่ใน worktree เดิมให้ทำต่อ (บอกว่าเหลืออะไรจาก diff) หรือทิ้งแล้วส่งใหม่
   - worktree ที่ไม่มีในบันทึก → ตรวจ ถ้าไม่มีอะไรมีค่า ลบ
4. รันด่านทั้งหมดบน `code-phase` ให้ผ่านก่อนเริ่มคลื่นใหม่
5. ทำต่อจาก "งานถัดไป"

**ทำงานยาวได้**

1. **ความจำอยู่ในไฟล์ ไม่อยู่ในบทสนทนา** บริบทของ session ถูกย่อได้ตลอด สิ่งที่ต้องรู้เพื่อทำต่ออยู่ใน `review/progress.md` `review/decisions.md` และไฟล์นี้ อ่านใหม่เมื่อไม่แน่ใจ
2. **คลื่นสั้น** คลื่นหนึ่งใช้เวลาไม่เกินราวสองชั่วโมงของ agent ถ้างานใหญ่กว่านั้น แบ่งเป็นคลื่นย่อย ติดเพดานแล้วเสียงานน้อย
3. **agent พร้อมกันไม่เกินห้าตัว** ลดการใช้เพดานพร้อมกัน และลดการชนตอนรวม ถ้าใกล้เพดานของรอบ (ดูได้จากการใช้งานของบัญชี) ลดเหลือสองถึงสามตัว
4. **รายงานของ agent สั้น** ตามแบบฟอร์ม 12.4 เพื่อไม่ให้บริบทของผู้นำเต็มเร็ว รายละเอียดอยู่ใน commit และไฟล์
5. **กลับมาทำต่อเอง** เริ่ม session ด้วย `/loop 1h <prompt ในหัวข้อ 17>` ลูปส่ง prompt ซ้ำทุกชั่วโมงเมื่อ session ว่าง ถ้าติดเพดาน ลูปจะลองอีกครั้งชั่วโมงถัดไปจนเพดานรีเซ็ต แล้วงานเดินต่อตามลำดับ "เมื่อกลับมาทำต่อ" ข้างบน ถ้าทำงานอยู่แล้ว prompt ของลูปบอกให้ทำต่อจากที่ค้าง
6. **เครื่องต้องตื่น** เปิดแอปและ session ทิ้งไว้ เปิด keep computer awake เสียบสายชาร์จ ไม่พับฝาเครื่อง
7. **หยุดเมื่อ** ทุกขั้นถึง M7 (M8 ต้องมีผู้เล่นจริง) หรือเหลือเฉพาะงานที่ต้องให้ผู้ใช้ตัดสินจริง ๆ เขียนรายงานสุดท้าย (หัวข้อ 16) แล้วหยุดลูป

## 16. รายงานสุดท้าย

ผู้ใช้ขอรายงานครั้งเดียวตอนจบ ไม่ต้องรายงานระหว่างทาง

### 16.1 หลักเมื่อแก้เอกสารเอง

1. แก้เพื่อให้ระบบสมดุลและสมเหตุสมผล ตามเป้าที่เอกสารตั้งไว้แล้ว ไม่เปลี่ยนแนวคิดหลักของเกม (หลักในหัวข้อ 1 ของ [../systems/god/README.md](../systems/god/README.md) เสาหลักห้าข้อใน [../systems/experience/README.md](../systems/experience/README.md) และสิ่งที่ผู้ใช้ตัดสินแล้วใน RAW_PLAN หัวข้อ 5)
2. ทุกการแก้มีเหตุผลที่วัดได้ (ผลของตัวจำลอง เป้าที่ไม่ผ่าน feedback ที่ซ้ำหลายบุคลิก) หรือเป็นการแก้ความขัดกันระหว่างเอกสาร
3. เปลี่ยนตัวเลขในขอบที่เอกสารตั้งไว้ได้เลย ถ้าต้องเปลี่ยนเป้า เขียนเหตุผลว่าทำไมเป้าเดิมวัดไม่ได้หรือไม่ตรงเจตนา (แบบที่ทำใน [../systems/god/06-implementation.md](../systems/god/06-implementation.md) หัวข้อ 4)
4. บันทึกทุกการแก้ใน `review/decisions.md` หนึ่งแถวต่อเรื่อง: วันที่ · ไฟล์และหัวข้อ · ก่อน · หลัง · เหตุผล · ผลที่วัดหลังแก้
5. บันทึกเรื่องสำคัญลงประวัติการตรวจ [consistency-checks.md](consistency-checks.md) ด้วยตามเดิม

### 16.2 แบบรายงาน

เขียนเป็น `review/final-report.md` และสรุปในข้อความสุดท้ายของ session

| ส่วน | เนื้อหา |
| --- | --- |
| ทำอะไรไป | ขั้นที่เสร็จ ระบบที่ทำงานได้ หน้าจอที่มี จำนวนภาพตัวละครและฉาก คำสั่งที่ใช้ลองเล่น |
| แก้อะไรไป | สรุปจาก `review/decisions.md` จัดกลุ่มตามระบบ ระบุการแก้ที่เปลี่ยนความรู้สึกของเกมมากที่สุดก่อน |
| Critical | เรื่องที่ผู้ใช้ต้องรู้หรือตัดสิน: ด่านที่ยังไม่ผ่าน ปัญหาระดับบล็อกที่ค้าง การแก้เอกสารที่อาจขัดกับเจตนาของผู้ใช้ ความเสี่ยงต่อขั้นถัดไป ค่าใช้จ่าย LLM ที่ใช้ไป |
| สถานะของขั้น | ตารางหัวข้อ 11 พร้อมสถานะจริง |
| ลองเล่นอย่างไร | คำสั่งเปิดเกม หน้าดีบัก storybook และเมล็ดที่น่าดู |

## 17. Prompt สำหรับ session ใหม่

**prompt เริ่มงาน** (วางเป็นข้อความแรก)

```
อ่าน docs/guide/code-plan.md ทั้งไฟล์ แล้วลงมือทำตามแผนตั้งแต่หัวข้อ 14 เป็น session ยาว
- ทำต่อเนื่องจนถึง M7 ตามหัวข้อ 11 โดยไม่ต้องหยุดถามระหว่างทาง แก้เอกสารเองได้ตามหัวข้อ 16.1 บันทึกใน review/decisions.md
- subagent ทุกตัวใช้ model: "sonnet" แบ่งงานตามหัวข้อ 12 และจบทุกคลื่นด้วยรอบตรวจของผู้เล่นจำลองหรือผู้ตรวจภาพตามหัวข้อ 12.6
- session นี้เป็นผู้นำ (Opus 5.5) ทำงานบนสาขา code-phase commit merge และ push ตามหัวข้อ 12.7 จบงานย่อยแต่ละชิ้นแล้ว push ทันที อัปเดต review/progress.md ทุกครั้ง (หัวข้อ 15) ข้อความ commit ไม่มีบรรทัด attribution
- ถ้าเริ่มใหม่หรือกลับมาหลังติดเพดาน ให้ทำตาม "เมื่อกลับมาทำต่อ" ในหัวข้อ 15 ก่อน (progress · git status · worktree ของ agent · ด่าน) แล้วทำต่อจากที่ค้าง
- เมื่อจบ เขียน review/final-report.md ตามหัวข้อ 16.2 แล้วสรุปว่าทำอะไรไป แก้อะไรไป และมี critical อะไรบ้าง
```

**ให้กลับมาทำต่อเองหลังเพดานรีเซ็ต** วางคำสั่งนี้เป็นข้อความแรกแทน prompt ข้างบน (ลูปส่ง prompt ทันทีหนึ่งครั้ง แล้วซ้ำทุกชั่วโมงเมื่อ session ว่าง)

```
/loop 1h อ่าน docs/guide/code-plan.md หัวข้อ 15 ถึง 17 และ review/progress.md (ถ้ายังไม่มี ให้เริ่มตามหัวข้อ 14) ตรวจ git status แล้วทำงานตามแผนต่อจากที่ค้างเป็น session ยาวตาม prompt เริ่มงานในหัวข้อ 17 ถ้างานถึง M7 แล้วและเขียน review/final-report.md เสร็จ ให้หยุดลูป
```
